# 系统分析与初步设计

系统分析要让读者从头到尾看懂“这个目标如何在当前系统里实现”。它不是需求摘要，也不是把实现全部推迟给详细设计。

## 写作目标

正文需要串起这条链：

```text
业务目标 -> 现有系统事实 -> 业务对象/模块关系 -> 端到端实现路径 -> 各端改动 -> 关键决策 -> 详细设计入口 -> 验收信号
```

复杂逻辑可以用 Mermaid；跨模块、需要编辑或复用的关系使用 `drawio-generator` 生成 `.drawio` 源文件，并在文档中链接图源。

## 图形工具选择

| 目的 | 工具 | 判断标准 |
|---|---|---|
| 在 Markdown 中说明短逻辑 | Mermaid | 节点少、关系稳定、只需随文阅读 |
| 交付正式系统图 | draw.io | 节点多、跨模块、需要编辑/复用/多人协作 |
| 探索或展示可视化结果 | `visualize` | 数据图表、模拟、关系展示或多个视觉方案比较 |
| 讨论页面视觉方案 | Visual Companion + Codex 视觉插件 | 页面草图、布局、表单、弹窗、视觉层级和空间关系 |

优先按目的选择：视觉方案讨论用 Visual Companion；可视化探索用 `visualize`；正式系统图用 draw.io；短逻辑说明用 Mermaid。`visualize` 不替代正式系统图，Visual Companion 也不替代最终交付图。

## 按项目实际选择维度

不是每个需求都填写所有维度。只展开真实涉及的部分；没有涉及就删除该节。

### 1. 业务目标与范围

说明用户场景、触发条件、最终结果、非目标和验收口径。不要只写“新增功能”，要写清谁在什么入口完成什么动作，系统产生什么结果。

### 2. 现状与差异

按“需求事实 / 代码事实 / 模型事实 / 运行态事实”区分证据，说明当前链路已经做到哪里、缺口在哪里。

### 3. 领域对象与关系

涉及 ePaaS 时，至少说明实际涉及的业务对象、主表/子表、关键字段、关联字段、有效性、开放对象和权限边界；说明对象之间是一对一、一对多还是通过中间对象关联。

以 AITR 陪练类需求为例，应明确产品、知识库、知识点、分析模型、任务/安排、人员或组织等对象之间的引用方向，以及哪些对象是配置源、哪些对象是运行时结果。

### 4. 端到端实现路径

从入口开始写到结果结束：

```text
用户/外部事件 -> Admin/移动端入口 -> API/事件 -> 服务端业务编排 -> 业务对象读写 -> 异步消息/Hook（如有） -> 查询/报表/页面结果
```

每一段至少给出实际模块、接口、事件、服务或对象名称；不要只写“后端处理”。

### 5. 模块与上下游

按实际涉及的端或模块展开：

- 服务端：入口、校验、事务、服务编排、Hook/Event/MQ、写入结果。
- Admin：菜单/路由、列表、表单、弹窗、详情、操作按钮、字段显隐和交互状态。
- 移动端或其他消费端：调用契约、字段、状态、兼容要求和是否需要同步修改。
- 其他模块：上游配置来源、下游消费方、回调、报表、通知和缓存。

前端不能只写“修改页面”。要说明新增哪个页面或区域、哪个表单字段、哪个弹窗、哪个按钮、请求什么接口、成功和失败后页面如何变化。

### 6. 状态、权限与异常

说明关键状态如何产生和流转，谁可以看/改/发布，空数据、重复提交、异步失败、历史数据和兼容行为如何处理。复杂状态用状态图表达。

### 7. 初步实现方案

给出足以指导详细设计的方案：修改入口、复用的现有机制、主要读写路径、关键判断、跨模块契约和不处理范围。这里不要求完整代码，但不能只写“增加服务”“增加校验”。

### 8. 详细设计映射

每个初步方案必须指向后续详细设计章节；详细设计必须从系统分析结论展开，不得引入未经确认的新业务规则。

## Plan 问答规则

- 只有会改变实现、接口、数据、权限、兼容或验收的未知项才提问。
- 发现未知项时立即在聊天中提问，不能只写在文档里等待用户查看。
- 用户回答后立即更新对应对象关系、实现路径、页面契约或验收口径，再继续分析。
- 未确认项不得进入依赖它的详细设计或开发 Task。

## 禁止

- 不写与实现无关的长背景、工具流水和泛化风险。
- 不用“相关模块”“增加接口”“完善页面”等词替代真实入口和关系。
- 不把所有字段、代码分支和测试步骤塞进系统分析；这些下沉到详细设计，但系统分析必须先把实现路径讲通。
