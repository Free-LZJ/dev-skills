# 方法子技能协同

需要判断是否使用 brainstorming、结构化调试、完成前验证或严格测试治理时读取本文件。

| 场景 | 方法 |
|------|------|
| 进入系统分析阶段，或存在会实质改变实现的关键歧义或真实方案取舍 | `brainstorming` |
| Bug、测试失败、运行异常或根因不清 | `systematic-debugging` |
| 声称完成、修复、通过或可交付前 | `verification-before-completion` |
| 用户明确启用 super / strict 的测试工作 | `$dev-test` |

## Brainstorming

进入系统分析阶段时自动调用。系统分析即使暂时没有关键歧义，也先用 brainstorming 识别并收敛真正影响实现的未知项；系统分析之外，只有用户明确要求，或关键未知项无法从需求、代码、模型和现有规则确认时才使用。

brainstorming 只解决会实质改变实现的关键选择：在聊天中给出证据、推荐和取舍后等待用户确认；不强制无意义的多轮提问、凑 2-3 个方案、逐节审批、额外 spec 文件或完整文档链。系统分析中的结论必须回写对应章节。

## Systematic Debugging

根因不清时先收集证据、定位触发链和共同入口，再提出修复。过程只在需要跨会话、审计或复盘时写入 `过程记录.md`；普通 Bug 直接在开发清单记录根因摘要和验证证据。

## Verification Before Completion

在完成声明前运行能证明当前结论的最新验证。验证证据优先写入开发清单；只有多环境、多阶段矩阵才维护测试计划。

## Super 模式

Super 模式下所有测试相关工作使用 `$dev-test`：

- 有明确工单目录时，测试报告正文以 `doc/<工单号>/*测试报告.md` 为权威源，`test-governance/` 仅保留项目需要的治理索引。
- 没有工单目录时，遵循 `$dev-test` 默认的 `test-governance/` 位置。
- requirements-delivery 只在开发清单记录测试状态、阻断摘要和报告路径，不复制测试正文。
- 缺少真实环境、账号、服务、数据或人工证据且影响结论时，保留阻断并向用户说明。

方法子技能负责方法纪律，requirements-delivery 负责最少必要的交付状态；不要重复生成两套产物。
