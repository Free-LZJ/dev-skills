# Task、审查与审计

编辑开发清单或需要保留审查、审计记录时读取本文件。

## Task 总览

`开发清单.md` 必须先提供总览：

| Task | 目标 | 设计定位 | 涉及模块 | 验收信号 | 设计 | 代码 | 验证 | 联调 | 当前状态 |
|------|------|----------|----------|----------|------|------|------|------|----------|

总览负责导航和状态汇总，不能替代 Task 明细。复杂业务使用父子 Task：父 Task 记录完整能力和汇总状态，子 Task 使用 `Task 1.1`、`Task 1.2` 等编号并分别记录范围、验收与证据；子 Task 全部完成后才能将父 Task 标记为已完成。

## Task 明细

总览中的每个 Task（包括父 Task 和子 Task）都必须有独立明细，至少包含：

- 目标。
- 实现描述。
- 设计定位。
- 核心代码或计划修改路径。
- 依赖。
- 验收口径。
- 阶段化状态及证据。
- 过程记录索引；没有过程记录时写 `不涉及`，不为填充格式创建文件。

设计定位字段不得省略。已创建 `详细设计.md` 或 `<阶段>-详细设计.md` 时，必须使用相对路径和锚点指向与该 Task 对应的具体章节；未创建详细设计时写 `不涉及（未创建详细设计）`。已有详细设计但定位缺失、失效或与 Task 不匹配时，先修正设计和开发清单，再进入实现。

## Task 拆分

Task 按可独立推进和验收的最小业务结果拆分；一个 Task 不要包含过多操作，多个无关目标不得混在一起。一个小结果涉及多个代码层时保持为同一子 Task，不按 Controller、Service、Hook、SQL、文档、测试等技术层机械拆分。

开发清单还必须包含依赖关系、推荐实施顺序和验证矩阵，使新会话不依赖聊天记录即可确定下一 Task 及其验收方式。

## 阶段化状态

每个 Task 使用阶段表，不用单个笼统状态替代：

| 阶段 | 状态 | 证据 |
|------|------|------|
| 设计 | 待完成 / 已完成 / 需调整 / 不涉及 | 具体设计章节或不涉及说明 |
| 代码 | 待实现 / 已完成 / 需调整 / 不涉及 | 文件或 PR / 提交 |
| 验证 | 待验证 / 已完成 / 失败待修复 / 不涉及 | 命令、场景或测试计划链接 |
| 联调 | 待联调 / 已完成 / 阻塞 / 不涉及 | 联调记录 |
| 生产验证 | 待验证 / 已完成 / 不涉及 | 运行态验证记录 |

## 状态更新

- 开始实现时更新对应 Task 明细的阶段状态，并同步总览中的当前状态。
- 验证成功后写入命令或场景摘要，更新验证阶段和总览汇总状态。
- 无法验证时标记 `待验证`，明确缺少的条件。
- 遇到阻断时记录阻断原因和解除条件。
- 验收口径变化时，将受影响 Task 退出 `已完成`。
- 父 Task 的状态从子 Task 汇总，不以父 Task 的空泛结论覆盖未完成子 Task。

总览只维护汇总状态，Task 明细维护阶段状态和证据；两者必须一致，但不复制长篇说明。

## 审查与审计

每个 Task 最多一次最终审计。普通状态汇报、探索、定向测试和中间 diff 检查不是最终审计，也不触发完成声明；完成声明必须等待最后一次相关代码变化后的新鲜验证。

普通代码复核不创建过程记录，只在 Task 证据中写结论。以下情况才写 `过程记录.md`：

- 用户要求审计、追责或复盘。
- 逃逸缺陷需要保留根因和改进措施。
- 长篇 Bug 历史对后续决策仍有价值。

过程记录可包含变更、根因、处理和证据。活跃开发清单只链接当前仍有影响的记录，不维护固定的“过程记录索引”空表。

## 验证证据

保留能支持结论的最小信息：验证命令或场景、结果、未覆盖范围。不要复制完整终端流水。存在 `测试计划.md` 或测试报告时直接链接。

Task 明细可用一行记录效率：`主动时间=<...>; token=<...>; 工具调用=<...>; 上下文压缩=<...>; 子代理=<...>`。
