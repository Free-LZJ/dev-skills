# Task、审查与审计

编辑开发清单或需要保留审查、审计记录时读取本文件。

## Task 结构

默认使用一张表：

| Task | 可交付结果 | 范围 | 验收信号 | 状态 | 证据 / 下一步 |
|------|------------|------|----------|------|---------------|

状态使用：`待处理`、`进行中`、`阻断`、`待验证`、`已完成`。只有联调、生产验证等阶段确实独立时，才增加阶段表。

Task 按独立业务结果拆分。一个结果涉及多个代码层时保持为同一 Task；多个无关目标不得混在一起。

详细设计链接是可选项：存在相关设计时引用，没有时不为满足格式补写设计文档。

## 状态更新

- 开始实现时可标记 `进行中`，不要求先同步其他文档。
- 验证成功后写入命令或场景摘要并标记 `已完成`。
- 无法验证时标记 `待验证`，明确缺少的条件。
- 遇到阻断时只记录阻断原因和解除条件。
- 验收口径变化时，将受影响 Task 退出 `已完成`。

不要在总览和 Task 明细重复维护同一状态。简单 Task 只保留表格行；复杂 Task 才增加必要说明。

## 审查与审计

普通代码复核不创建过程记录，只在 Task 证据中写结论。以下情况才写 `过程记录.md`：

- 用户要求审计、追责或复盘。
- 逃逸缺陷需要保留根因和改进措施。
- 长篇 Bug 历史对后续决策仍有价值。

过程记录可包含变更、根因、处理和证据。活跃开发清单只链接当前仍有影响的记录，不维护固定的“过程记录索引”空表。

## 验证证据

保留能支持结论的最小信息：验证命令或场景、结果、未覆盖范围。不要复制完整终端流水。存在 `测试计划.md` 或测试报告时直接链接。
