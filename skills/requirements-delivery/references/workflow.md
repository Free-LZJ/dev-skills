# 工作流与恢复

## 轻量

读取规则、需求和相关代码，直接实现，运行最小验证，汇报改动和未验证范围。不创建流程文档。

## 跟踪

仅在多 Task、跨会话或需要明确交付状态时创建 `开发清单.md`。

1. 先读总览和当前活跃 Task。
2. 按业务结果选择一个可独立验收的 Task。
3. 需要跨模块方案时，先读 `系统分析.md` 和 `详细设计.md` 对应章节。
4. 实现、验证，再更新该 Task 的状态和证据。
5. 发现其他 Task 的问题只记录，不顺手扩展范围。

Task 只保留一份阶段状态。总览可以显示摘要，但不再复制完整阶段表。Task 变更文件超出原范围时，先说明原因并更新范围，再继续。

## 设计顺序

系统分析是面向项目的初步设计：说明业务对象、模块边界、上下游关系、端到端链路和页面/契约改动。详细设计从系统分析已确认的方案展开到具体文件、方法、字段、分支和验证。开发清单再从详细设计反推 Task 和顺序。

没有完成系统分析的实现路径，不进入详细设计；没有达到可直接实现粒度的详细设计，不进入实现。

## 新会话恢复

按以下顺序读取：

1. 仓库规则。
2. `开发清单.md` 的总览和活跃 Task。
3. 当前 Task 关联的系统分析、详细设计章节。
4. 最近验证证据和未解决阻断。

只有清单无法表达复杂恢复信息时才创建或读取 `当前上下文.md`。不依赖聊天记忆猜测状态。

## 验证

验证范围从受影响代码开始；风险、失败或仓库规则要求时再扩大。完成、提交或创建 PR 前必须对最后一次相关变更运行一次新鲜验证。验证证据写入当前 Task；只有多环境、多阶段矩阵才创建 `测试计划.md`。
