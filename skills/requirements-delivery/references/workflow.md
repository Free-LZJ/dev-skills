# 工作流

需要选择流程级别、恢复跨会话任务或推进实现与验证时读取本文件。

## 选择最轻流程

默认使用轻量流程。只有当前任务需要状态跟踪、关键设计或严格测试治理时才升级，不因存在工单号或需求文档自动升级。

| 信号 | 处理 |
|------|------|
| 目标明确、影响集中、当前会话可完成 | 轻量流程 |
| 多个独立交付结果或需要跨会话 | 增加 `开发清单.md` |
| 跨模块契约、迁移、权限、并发、回滚或重大方案取舍 | 按需增加分析或详细设计 |
| 用户明确要求 super / strict | 使用 `$dev-test` 的严格测试治理 |

## 轻量流程

1. 读取仓库规则、需求和相关代码。
2. 只询问阻断实现的问题；低风险细节采用现有模式。
3. 实现完整业务结果，不为流程创建文档。
4. 运行最小有意义验证。
5. 汇报改动、证据和未验证项。

## 跟踪流程

1. 读取已有 `开发清单.md` 的总览、依赖关系、推荐顺序和活跃 Task 明细；没有时仅在确需跨会话或多 Task 跟踪时创建。
2. 选择一个可独立验收的活跃 Task，核对其设计定位、阶段状态和验收口径。已创建详细设计时，设计定位必须指向对应的具体章节；未创建时必须明确写 `不涉及（未创建详细设计）`。
3. 设计定位缺失、失效、与 Task 不匹配，或当前复杂度需要详细设计但尚未设计时，先修正详细设计和开发清单，不直接实现。
4. 有具体设计章节时先读取该章节，再读取直接相关的需求或分析结论，实现并验证该 Task。
5. 同步更新 Task 明细、总览汇总状态和验证矩阵；父 Task 状态由子 Task 汇总。
6. 仅当关键结论发生变化时更新其权威文档；其他文档通过链接引用，不复制长篇内容。

## 分析与设计

系统分析回答“需求与真实现状有什么差异、边界和风险是什么”。详细设计回答“高风险或跨模块部分具体如何实现”。两者不重复；创建详细设计时要尽量写到实施者可直接落地：关键实现给出代码片段或完整伪代码，较长的读写、调用或状态流转给出 Mermaid，并提供可被开发清单逐 Task 引用的稳定章节。

- 需求明确且现有架构已决定方案时，不创建系统分析。
- 局部实现无需跨模块契约时，不创建详细设计。
- 进入系统分析阶段，或关键未知项会改变实现时使用 brainstorming。
- 会实质改变实现、接口、数据、权限、兼容或验收口径的决策必须在聊天中等待用户确认；只有低风险、可撤销的细节可采用可逆默认。
- 设计变化时只更新受影响的权威章节和开发清单，不机械同步全部文档。

## Task 拆分

按可独立推进和验收的最小业务结果拆分，例如“完成模板保存校验”或“页面接入真实分页数据”。不要把多个操作堆入一个 Task。

复杂业务可以使用父子 Task：父 Task 只汇总一个完整业务能力，子 Task 按可独立交付结果拆分；例如“主数据管理”下拆“服务端读写与校验”“列表查询”“新增编辑”“删除保护”。父、子 Task 都必须有独立明细和设计定位。不要为了层级而按 Controller、Service、Hook、SQL、文档、测试等技术层机械拆分；只有它们本身能独立验收时才单列。

## 新会话恢复

优先读取：

1. 仓库规则。
2. `开发清单.md` 的总览、依赖关系、推荐顺序和活跃 Task 明细。
3. 活跃 Task 的设计定位指向的具体章节，以及直接相关的需求或分析结论。
4. 活跃 Task 的阶段状态、验证矩阵、必要代码和最近验证证据。

设计定位缺失或失效时先补齐设计和开发清单，不依赖旧会话记忆猜测实现。

只有开发清单无法表达复杂阻断或多阶段恢复信息时才读取 `当前上下文.md`。默认不读取 `过程记录.md`。

## Bug 与验证

- 根因不清、测试失败或运行异常时使用 `systematic-debugging`，先定位根因再修改。
- 声称完成前使用 `verification-before-completion`，运行能证明结论的最新验证。
- 验证从受影响范围开始，只有风险、失败或仓库规则要求时扩大。
- 普通验证证据写入开发清单；只有多环境、多阶段矩阵才创建 `测试计划.md`。

## 状态同步

`sync` 表示把当前真实代码和验证状态写回唯一状态源，不代表刷新所有文档。发现文档与代码不一致时，以已验证事实为准并修正权威结论。

不要自动提交。用户要求提交时重新读取仓库 VCS 规则并确认变更边界。
