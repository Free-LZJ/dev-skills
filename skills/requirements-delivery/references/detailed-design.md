# 详细设计写作规则

详细设计的完成标准是：开发者看完后可以直接定位代码并开始实现。抽象描述、模块名列表和“增加校验/调用服务”不算设计。

## 每个实现点必须写

1. **业务结果**：这一点完成后用户或系统看到什么变化。
2. **入口**：接口、事件、页面操作、定时任务或消息入口。
3. **修改位置**：具体文件、类、方法、组件、模型或 SQL。
4. **调用链**：当前链路和修改后链路，必要时用 Mermaid。
5. **输入输出**：字段来源、类型、空值语义和返回结果。
6. **实现步骤**：按实际执行顺序写校验、读取、计算、写入和通知。
7. **关键代码**：给出可翻译成代码的代码片段或覆盖关键分支的完整伪代码。
8. **异常与边界**：失败、重复、空数据、权限和兼容行为。
9. **验证**：具体命令、接口、页面操作或数据断言。

## 推荐结构

```text
### 1. 结果
### 2. 入口与修改位置
### 3. 调用链
### 4. 数据与状态变化
### 5. 实现步骤
### 6. 关键代码 / 伪代码
### 7. 异常、兼容与回滚
### 8. 验证
```

## 约束

- 一个章节只解决一个可独立实现的结果。
- 不按 Controller、Service、SQL、文档机械拆章节；按业务结果拆。
- Mermaid 只在文字难以表达调用链、状态机或复杂数据流时使用。
- 不复制系统分析背景，不写无法映射到文件或入口的“架构愿景”。
