# Requirements Delivery

用满足当前任务所需的最轻流程完成交付。默认直接推进，只有文档能减少真实风险或支持跨会话恢复时才创建。

## 交付信封（不可扩张）

跟踪级或设计级 Task 开始时先声明唯一 Task 标识，并固定五项：允许文件、不处理范围、验证命令、停止条件、当前阻断。未列出的文件不改；跨 Task 发现只记录阻断，不顺手实现。验证命令必须在最后一次相关代码变化后新鲜运行。默认不启动子代理；“并行”只表示工作可并行，不授权自动 `spawn_agent`。一次上下文压缩后必须回读信封、活跃 Task、阻断和下一步；无法恢复就停止。

每个 Task 最多一次最终审计。探索、状态汇报和中间检查不等同于完成声明。Task 收口只保留一行效率记录：主动时间、token、工具调用次数、上下文压缩次数、子代理数量；不创建大报告或过程文档。

Codex Hook 现状：已核对当前桌面配置和已启用 Ponytail 插件，能确认 `SessionStart`/`UserPromptSubmit` 的插件级 hook，但没有项目侧可验证的 Codex Desktop `PreToolUse` 注册契约；因此本 Skill 不伪造 Hook 配置，也不声称能自动阻断未授权 `spawn_agent` 或重复验证。若宿主以后提供稳定契约，优先在 SessionStart/UserPromptSubmit 注入本信封，PreToolUse 只做确定性阻断，并用宿主提供的 dry-run/事件日志验证。

如果用户只提供工单号，到 `doc/<工单号>/` 查找已有文档；用户指定路径时以用户路径为准。不要仅因启用本 skill 创建完整文档集。

## 流程分级

| 级别 | 适用场景 | 默认产物 |
|------|----------|----------|
| 轻量 | 目标明确、影响集中、可在当前会话完成 | 不新增流程文档；直接实现并验证 |
| 跟踪 | 多个可独立交付结果、需要跨会话继续 | `开发清单.md` |
| 设计 | 存在跨模块契约、关键方案取舍、迁移或高风险边界 | 按需增加 `系统分析.md` 或 `详细设计.md` |
| Super | 用户明确要求严格测试治理或 `super模式` / `--super` | 在上述基础上使用 `$dev-test` 留存测试资产 |

`fast模式`、`--fast`、`快速模式` 视为明确选择轻量级别；轻量本身就是默认，不要求用户额外声明。

## 文档边界

- `开发清单.md`：跟踪级别的唯一任务状态源；固定包含 Task 总览、依赖关系、推荐实施顺序、逐 Task 明细、阶段化状态和验证矩阵。Task 细化为可独立推进和验收的最小业务结果，复杂事项使用父子 Task；每个父、子 Task 都必须保留设计定位。
- `系统分析.md`：仅记录需求与代码/模型真实状态的差异、关键结论、边界和风险；目标明确时不创建。
- `详细设计.md` / `<阶段>-详细设计.md`：仅用于跨模块契约、复杂数据流、迁移、权限、并发或回滚设计；创建后尽量写到可直接实现，覆盖关键代码或完整伪代码，较长流程附 Mermaid。已创建详细设计时，每个 Task 的设计定位必须索引对应的具体章节；未创建详细设计时写明 `不涉及（未创建详细设计）`，不为填充格式强造设计。
- `当前上下文.md`：仅在开发清单不足以支持长周期或多人恢复时创建，保存活跃 Task、有效结论、阻断和下一步，不复制状态历史。
- `测试计划.md`：仅在存在多环境、多阶段或多类型验证矩阵时创建；普通验证证据直接写入开发清单。
- `过程记录.md`：仅用于审计、复盘和需要保留的长篇 Bug 历史，默认不创建、不读取。

同一状态只维护一处。其他文档引用权威结论，不机械复制，也不要求每次代码修改前后同步全部文档。

## 核心流程

1. 阅读仓库规则、需求来源和相关代码，区分文档假设、代码真实状态与已验证的运行态事实。
2. 自动选择最轻级别；除非用户明确要求，不为流程升级停下来征求许可。
3. 会改变实现、权限、安全、数据、兼容或验收口径的未知项必须通过 `brainstorming` 在聊天中向用户确认；推荐方案不能代替用户回答。其余低风险且可撤销的细节才采用可逆默认并说明。
4. 需要跟踪时，先建立 Task 总览，再按可独立推进和验收的最小业务结果补齐逐 Task 明细；复杂业务以父 Task 汇总，再按增删改查、服务端、前端等可独立交付结果拆子 Task，避免单个 Task 包含过多操作。每个父、子 Task 都必须记录设计定位、依赖、验收口径、阶段状态和验证证据。
5. 直接实现当前目标。只有实现改变了已确认的关键契约时，才先更新对应权威文档。
6. 运行最小有意义验证；扩大验证范围必须由风险或仓库规则驱动。
7. 只更新开发清单中的当前状态和必要证据；长篇过程按需进入过程记录。
8. 汇报已完成内容、验证结果、未验证项和阻断，不自动提交。

## 澄清与设计

进入系统分析阶段时必须先使用 `brainstorming`。除此之外，以下情况才使用 `brainstorming`：用户明确要求；存在两个以上会实质改变实现的可行方案；关键业务边界无法从需求、代码或模型确认。

未进入系统分析阶段且目标明确、方案由现有架构决定、局部配置/文档修改或已有根因的 Bug 修复，不调用 brainstorming。需要时只澄清关键选择，不强制多轮提问、2-3 个方案、逐节审批或额外设计文件。

系统分析必须在正文保留 `Brainstorming 结论` 表，逐项记录关键未知项、候选方案、推荐与取舍、结论状态、依据和验收信号。结论状态只使用 `已确认`、`可逆默认`、`待确认`、`阻断`。

存在 `待确认` 时，先在聊天中给出证据、推荐和取舍并询问用户；收到回答后再更新结论状态和继续依赖该决策的分析。不得把“需产品复核”“后续确认”或 AI 自选推荐方案记为 `已确认` / `可逆默认`。

只有关键结论均为 `已确认` 或 `可逆默认`，且不存在结构化的 P0、待确认、需复核、阻断项或失效相对链接时，分析状态才能标记为 `已完成`；否则使用 `进行中`、`待复核` 或 `阻断`。声明系统分析完成前，使用 `verification-before-completion` 运行 `python <requirements-delivery>/scripts/validate_system_analysis.py <系统分析.md>`，校验失败时不得完成。

## Super 模式

只有用户明确说 `super模式`、`--super`、`超级模式` 或“严格模式”时启用：

- 所有测试相关工作使用 `$dev-test`。
- 有明确工单目录时，测试报告正文放在 `doc/<工单号>/*测试报告.md`，`test-governance/` 只保留项目确实需要的治理索引；没有工单目录时遵循 `$dev-test` 默认位置。
- `开发清单.md` 只记录测试状态、阻断摘要和报告路径，不复制测试正文。
- 缺少真实环境、账号、服务或数据且会影响验证结论时，按 `$dev-test` 规则报告阻断。

## Skill 协同

- Bug、测试失败、运行异常或根因不清时使用 `systematic-debugging`。
- 声称完成、修复、通过或可交付前使用 `verification-before-completion`。
- ePaaS、DataRecord、SQL 和测试专项规则交给对应专科 skill，不在本 skill 重复维护。

不要自动提交。用户要求提交时，重新读取仓库 VCS 规则并确认 staged、unstaged 和 untracked 边界。
