# Requirements Delivery

最轻的流程仍然包含**分诊、决策闭合、验证**三件事；被省略的只能是文档和阶段，不是这三件。

## 启动动作（第一个回复必须包含，不可跳过）

在读取代码或调用任何写入工具前，先输出这三行：

```text
级别：轻量 | 跟踪 | 设计
理由：<一句话>
决策闭合：无未知项 / 待确认：<问题原文>
```

- 判 `轻量` 时必须写清“为什么不存在会改变接口、数据、权限、兼容或验收的未知项”。写不出这句，就不是轻量。
- 级别一旦声明，之后升级或降级都要在正文说明原因。
- 没有这三行就开始读代码或改文件，视为流程违规；读者应拒收该轮结论，要求重新分诊。

## 阶段与允许动作

| 阶段 | 允许 | 禁止 |
|---|---|---|
| 分析（跟踪 / 设计） | read、grep、glob、写流程文档、`ask_user_question` | 改生产代码、跑会改代码的生成器 |
| 决策闭合 | `ask_user_question` 阻塞等待 | 用正文提问代替、带着猜测继续实现 |
| 详细设计 | 写详细设计文档 | 跳过系统分析直接详细设计 |
| 实现 | 按详细设计改代码 | 出现新未知项仍继续实现 |
| 验证 | 跑测试与校验脚本 | 没有验证证据就声称完成 |

设计级在 `系统分析.md` 产出并通过下面出口校验前，**不得修改生产代码**。

## 阻塞提问（唯一合法方式）

发现会改变接口、数据、权限、兼容或验收的未知项时：

1. 调用 `ask_user_question`，一次只问一个最关键的问题，附事实、推荐、取舍。
2. 工具返回后再继续依赖该答案的工作。
3. 不允许把问题写进正文后继续实现；不允许把推荐方案当成用户确认。

宿主处于 Plan 模式时，用 `exit_plan_mode` 交付分析并等待批准；不在 Plan 模式时，`ask_user_question` 就是等价阻塞点。不要声称“已自动进入 Plan 模式”——模型无法自行切换宿主模式。

## 进入实现前的出口校验

```bash
python <本 skill 目录>/scripts/validate_system_analysis.py <系统分析.md>
```

- 退出码非 0：存在未闭合决策或结构缺失，**不得进入实现**，回到阻塞提问。
- 退出码 0：可进入详细设计或实现。
- 轻量级没有系统分析文件时跳过脚本，但启动动作的“决策闭合”行必须说明为什么不需要。

## 级别

| 级别 | 适用 | 产物 |
|---|---|---|
| 轻量 | 当前会话可完成、影响集中 | 直接实现、验证、汇报 |
| 跟踪 | 多个可独立验收结果或跨会话 | `开发清单.md` |
| 设计 | 关键边界或跨模块实现需要先定方案 | `系统分析.md`、`详细设计.md` 按需创建 |
| Super | 用户明确要求 `super` / `strict` 测试治理 | 读取 `$dev-test` 规则 |

`fast` / `快速模式` 等同轻量。设计不是额外阶段；它只是在实现前增加必要的分析或设计文档。判轻量的门槛见启动动作，不用于绕过分诊。

## 主流程

1. 读仓库规则、需求来源、相关代码、运行态证据（只读）。
2. 输出启动动作三行，确定级别。
3. 跟踪 / 设计级进入只读分析，按 `references/system-analysis.md` 形成初步设计。
4. 遇到改变实现的未知项，按“阻塞提问”处理；用户回答后立即回写系统分析。
5. 分析状态置为“已完成”前跑出口校验，非 0 不继续。
6. 按系统分析写详细设计，再拆最小业务 Task，实现并验证。
7. 回写状态、验证证据和未覆盖范围；用户未要求时不提交。

## 待确认决策硬门禁

在进入详细设计、实现或完成收口前，必须重新读取系统分析的待确认决策与开发清单：

1. 存在 `待确认`、`阻断`、`需复核` 时，先给出事实、推荐、取舍，再 `ask_user_question` 问一个关键问题。
2. 用户回答前，只做不依赖该决策的只读工作；不得继续写依赖它的设计、实现、联调或发布结论。
3. 未确认项不得改写成 `已确认`、`可逆默认` 或“已完成”；不得报告 Task 完成。
4. 每次完成/提交前跑出口校验；存在未闭合决策时，分析与清单保持待复核或进行中。

## 产物路由

- 系统分析：读取 `references/system-analysis.md`、`references/plan-mode.md`、`references/brainstorming.md`；系统分析是初步设计，不是只列风险的摘要。
- 详细设计：读取 `references/detailed-design.md`。
- 需要表达复杂流程、状态机、调用链或数据流时，读取并使用 `drawio-generator`；简单图示可直接用 Mermaid。
- 图形工具按目的选：短逻辑用 Mermaid，正式可编辑系统图用 draw.io，可视化探索用 `visualize`，页面草图和视觉方案讨论用 `visual-companion` 与 Codex 视觉插件。
- 需要交互式页面草图、视觉方案对比或空间关系讨论时，读取 `references/visual-companion.md`；它与 Codex 视觉插件互补。
- Task、恢复和状态：读取 `references/workflow.md`、`references/document-set.md`、`references/task-review-audit.md`。
- Bug、失败或根因不清：读取 `references/superpowers-coordination.md`，再使用 `systematic-debugging`。
- 声称完成、修复、通过或可交付前：使用 `verification-before-completion`。

## 发布清单（涉及 pre / prod 发布时必做）

需求要上线时，`开发清单.md` 必须包含发布清单章节，并**按改动类型全覆盖**，不能只写代码：

| 类型 | 必须回答 |
|---|---|
| 代码 | 涉及哪些仓库、分支、提交；发布顺序与依赖关系 |
| 模型 | 是否有字段、表、索引变更；各环境是否要单独 field-add + activate 执行 DDL |
| 配置 | Nacos / 环境变量 / 开关的键、默认值、各环境是否需显式配置 |
| 数据 | 是否需要一次性升级脚本或回填；定时任务能否覆盖这类数据 |
| 外部依赖 | 第三方资源、凭证、场景或渠道配置在目标环境是否就绪 |

- 任一类没有改动，也要写“无变更”并给出依据，不允许留空。
- 不允许用“代码已发布”代替模型、配置、数据的核对；这几类不会随代码发布自动生效。
- 每类要写清执行方式与验证方式；跨环境的按环境分别列。
- 涉及写数据或改配置的动作，标明是否可重跑、是否有配额或上限。

## 完成标准

- 启动动作三行、决策闭合和验证证据在会话里可追溯。
- 系统分析能说明“为什么改、改哪里、验收什么”。
- 详细设计能让开发者直接改代码，不需要重新猜入口、文件、调用链或数据语义。
- Task 状态和验证证据与实际代码一致。
- 涉及发布时，发布清单覆盖代码、模型、配置、数据、外部依赖五类，且每类有执行与验证方式。
