# Requirements Delivery

只使用完成当前任务所需的最轻流程。先读规则、需求和相关代码，再按真实风险选择级别；不要因为有工单号就自动创建文档集。

## 级别

| 级别 | 适用 | 产物 |
|---|---|---|
| 轻量 | 当前会话可完成、影响集中 | 直接实现、验证、汇报 |
| 跟踪 | 多个可独立验收结果或跨会话 | `开发清单.md` |
| 设计 | 关键边界或跨模块实现需要先定方案 | `系统分析.md`、`详细设计.md` 按需创建 |
| Super | 用户明确要求 `super` / `strict` 测试治理 | 读取 `$dev-test` 规则 |

`fast` / `快速模式` 等同轻量。设计不是额外阶段；它只是在实现前增加必要的分析或设计文档。

## 主流程

1. 读取仓库规则、需求来源、相关代码和运行态证据。
2. 判断是否需要跟踪或设计；不需要就直接实现。
3. 进入系统分析时自动开启 Plan 模式；发现会改变接口、数据、权限、兼容或验收的事项，直接在聊天中向用户提问，等回答后回写系统分析。
4. 系统分析确认实现方式和模块关系后，再按系统分析编写可直接编码的详细设计。
5. 详细设计稳定后，按详细设计拆分最小业务 Task，再实现和验证。
6. 回写当前状态、验证证据和未覆盖范围；用户未要求时不提交。

## 待确认决策硬门禁

在进入详细设计、实现或完成收口前，必须重新读取系统分析的待确认决策和开发清单：

1. 发现 `待确认`、`阻断` 或 `需复核` 的决策时，先在聊天中给出事实、推荐和取舍，向用户提问一个关键问题。
2. 用户回答前，只能继续明确不依赖该决策的独立工作；不得继续编写依赖项的设计、实现、联调或发布结论。
3. 未确认项不得改写为 `已确认`、`可逆默认` 或“已完成”；不得调用完成收口或把 Task 报告为完成。
4. 每次完成/提交前运行系统分析校验；存在未闭合决策时，必须保持分析/清单为待复核或进行中。

## 产物路由

- 系统分析：读取 `references/system-analysis.md`、`references/plan-mode.md` 和 `references/brainstorming.md`；系统分析是初步设计，不是只列风险的摘要。
- 详细设计：读取 `references/detailed-design.md`。
- 需要表达复杂流程、状态机、调用链或数据流时，读取并使用 `drawio-generator`；简单图示可直接使用 Mermaid。
- 图形工具按目的选择：短逻辑用 Mermaid，正式可编辑系统图用 draw.io，可视化探索用 `visualize`，页面草图和视觉方案讨论用 `visual-companion` 与 Codex 视觉插件。
- 需要交互式页面草图、视觉方案对比或空间关系讨论时，读取 `references/visual-companion.md`；它与 Codex 视觉插件互补。
- Task、恢复和状态：读取 `references/workflow.md`、`references/document-set.md`、`references/task-review-audit.md`。
- Bug、失败或根因不清：读取 `references/superpowers-coordination.md`，再使用 `systematic-debugging`。
- 声称完成、修复、通过或可交付前：使用 `verification-before-completion`。

## 完成标准

- 系统分析能说明“为什么改、改哪里、验收什么”。
- 详细设计能让开发者直接开始改代码，不需要重新猜入口、文件、调用链或数据语义。
- Task 状态和验证证据与实际代码一致。
