# 超进化

用于开发流程自治纠偏。完成条件是修复已授权的问题，并让后续同类任务实际获得且执行有效约束。报告只承载证据，篇幅按问题影响决定；不要把写总结、新增文档或罗列待办作为完成条件。

## 责任诊断与自主行动

- 先确认用户是在要求诊断还是修复。用户已要求修复及进化时，相关本地代码、rule、skill 和检查器修改连续完成，不再逐阶段请求确认；不因此扩大到无关配置、远端发布或数据写入。
- 沿全部调用方追踪输入来源、类型、信任边界及平台行为，并通过 diff、blame/log、可获取的原会话与检查结果定位引入点。区分当前工作区改动和历史提交。
- 检查任务提示词、系统分析/需求、最近规则、实际选择的 skill、插件能力、记忆、上下文恢复、实现、测试和审查。只报告相关证据；找不到历史加载、测试通过或上下文丢失证据时标为未证实，禁止编造归因。
- **约束缺失或错误**：在最近必读 rule 或专项 skill 修正决策边界；**存在但未加载**：修触发描述、规则索引或安装链接；**已加载但未执行**：修开发自检/审查入口，能够机械判断时接入现有检查器，不继续堆同义规则。
- **测试/工具盲区**：补能暴露旧问题的最小检查。行为错误用行为测试，类型边界优先用编译，代码风格用扫描及调用链审查；不为纯删减堆 mock 测试，也不把扫描通过当运行验收。
- **上下文问题**：核对中断/压缩前后哪些必要事实未恢复；经证实后把恢复动作接到任务必经入口。长期记忆只在用户明确要求记忆更新时按宿主规则写入，不以“进化”自动授权记忆写入。不能修改系统提示词或模型本身时，在可控入口补措施并说明能力边界。
- 修改安装技能前解析符号链接到真实来源，保留已有改动；修改后从实际安装入口读回确认。只改未加载副本不算完成。

最终简述修复结果、AI 责任与有证据的漏检原因、已生效的措施和验证边界，附关键路径/命令；待执行措施必须有真实阻断原因。没有必要的业务契约变化时不新增复盘文档。

## 执行流程

1. 先止血。
   - 定位正在失败的代码路径和真实错误。
   - 对 SQL 错误必须检查渲染 SQL、参数顺序、参数 Java 类型、数据库字段类型和 PostgreSQL 运算符兼容性。
   - 若不能连真实库，至少在测试中断言渲染 SQL 中的显式 cast 和参数类型。

2. 再追责。
   - 系统分析是否遗漏类型兼容、运行态验证或真实表结构。
   - skill 是否给了错误/不足指引，例如只要求语法正确但没有要求参数类型验证。
   - 插件或工具是否只能做静态检查，不能证明运行可用。
   - 会话记忆或本地规则是否记录了错误前提。
   - 代码审查是否只看结构和片段，未审参数类型和执行语义。
   - 测试是否 mock 掉数据库，只验证调用和片段，未验证 SQL 可执行性。

3. 然后改进。
   - 修代码。
   - 选择与根因匹配的最小验证，先确认旧样本失败或告警，再确认修复后通过；涉及上下文判断的扫描只能提示人工审查，不能伪装成类型或业务语义分析。
   - 把可复用约束写入实际会在后续任务中加载的最近 rule 或专项 skill；能够机械判断时同步更新检查脚本。
   - 运行新增或修改后的规则入口，确认其实际扫描目标文件并能命中旧问题；规则文本存在但未加载、检查脚本提前退出或扫描数为零都不算闭环。
   - 只有业务事实、需求契约、Task 状态或验证证据发生变化时才更新对应业务文档。

## 自治闭环与归档边界

每次触发超进化时，按以下顺序决定改进落点：

1. 先定位后续同类任务必经的规则注入入口，例如最近 `AGENTS.md`、其索引的 `rules/*.md` 或必触发的专项 skill。
2. 仓库特有的编码、文档和验证约束写入最近 rule；跨仓库的代理行为写入对应 skill；可正则、AST、编译或测试判断的约束写入检查器。
3. 验证“会加载、会执行、会失败”：确认入口显式引用规则，运行检查器并用旧问题样本验证能够产生 failure 或 warning。
4. 删除业务需求文档、产品文档和开发清单中的 AI 责任、漏检链路、提示词复盘和防复发叙述。这些文档只保留业务事实、契约、状态和验证证据。
5. 若现有 skill 指令本身诱导错误，必须优先修正 skill，再修仓库规则，避免只在单个项目留下补丁。
6. 收尾前复跑实际开发检查入口，确认覆盖修改文件且旧问题样本能被命中；同时用一个合理的边界场景检查新约束没有误禁正常需求。若仍漏检，继续修入口或检查器，不能仅记录“以后注意”。

## 平台能力重复实现逃逸最低标准

遇到用户指出“平台已有能力”“不要重复实现”“冗余 VO/实体/分页载体”“不要脱裤子放屁”等问题时，必须检查：

- 公开 API 返回类型是否仍包裹了平台已有的分页、列表、转换或参数结构，例如只重复 `page/pageSize/totalRow/totalPage/hasMore/list` 的 `ListVO/PageVO/PagedXxx`。
- 代码是否只删除了内部临时结构，却保留了对外冗余结构，导致审查误判为已复用平台能力。
- 测试是否把冗余结构当成正确协议继续断言，掩盖架构问题。
- 系统分析和开发清单是否只写“复用平台能力”，但没有明确禁止同类冗余外壳。
- 若确需额外字段，必须说明该字段为什么不能由平台结构、前端派生或独立详情接口承载。

## 禁止事项

- 禁止只说“已修复”而不解释来源和责任。
- 禁止把测试通过当作 SQL 可运行的证明，除非测试连接真实数据库或显式验证渲染 SQL 与参数类型。
- 禁止把严重问题只记录在聊天里；可复用约束必须沉淀到 rule、skill 或检查器，项目事故事实仅在确有长期维护价值时归档到 Bug 文档。
- 禁止默认把 AI 责任、漏检链路或防复发过程写入需求文档、产品文档、开发清单或代码注释。
- 禁止只增加规则文字而不验证注入入口和执行结果；能够机械检查的问题必须优先形成可执行门禁。
- 禁止把整个分支、目录或工作区 clean 当作单个 Task 提交完整性的门禁。提交遗漏类问题只按当前 Task 已确认的文件/hunk 清单与对应提交差异对账；其他 Task 的 staged、unstaged、untracked 改动允许保留，归属未决时逐项查源，不清理也不夹带。
